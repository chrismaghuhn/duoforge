### 2.2 Proposal: the constant becomes a capacity

- `DUOFORGE_ACTIVE_PER_SIDE` keeps the value 2 and its meaning **"the capacity of every position array"**. The header
  comment says so; no struct changes size, no offset moves, `python/duoforge/_layout.py` is unchanged, and the layout
  test stays green without an edit.
- The game type comes from the **data kind**, the existing format switch of the context: a new kind
  `DUOFORGE_DATA_KIND_<HS: GEN9OU>` (and `_DEV`, and a Champions-singles development kind, section 9). A new kind is an
  addition, not a change: every existing kind keeps its behaviour and its bytes.
- A query `duoforge_context_active_per_side(ctx)` `<HS: name>` returns 1 or 2, so callers do not derive the game type
  from a kind table of their own. It allocates nothing and is an added symbol (P6 lists it).
- Under a singles kind:
  - Flat positions stay `side*2+slot`; **slot 1 of each side is never occupied**. The view writes it as an empty
    position (`occupant` = `DUOFORGE_ROSTER_NONE`, the ext block all zero, as for an empty position today), the factored
    domain has `slot_count[1] = 0`, and slot 1 of a side choice is always `DUOFORGE_SLOT_NONE` ("an unrequested slot",
    `duoforge.h:539`). A command that fills slot 1 is `E_INVALID_ARGUMENT`.
  - `MAX_CANDIDATES` (784) is far above the singles bound: 4 moves × 2 (Tera) + 5 switches = 13.
  - Target classes follow Showdown's singles resolution: `adjacentFoe`, `any`, `randomNormal`, `allAdjacentFoes` and
    `allAdjacent` resolve to the one foe; `adjacentAlly` fails; `adjacentAllyOrSelf` and `allies` are the user. The
    spread modifier never applies because there is never more than one target. Redirection and ally abilities do
    nothing because no ally exists. This is **not** a switch per mechanic: the rules stay the same, only the set of
    occupied positions differs. Where the current code assumes an ally exists without checking for an occupant, that
    code is a bug that the singles conformance set finds.
  - **Team preview:** 6 of 6. In singles only the lead matters; the order of the bench is the registered order. The
    TEAM_SELECTION domain under a singles kind is the **6 leads**, not the 720 orders that `dfi_enumerate_team` would
    produce. The engine owns this rule, never Python.
  - Replacement and pivot boundaries are unchanged in kind; they request one position instead of up to two.
- **Why not change the constant:** `DUOFORGE_ACTIVE_PER_SIDE = 1` would change about 15 public structs, the encoder
  widths, the batch strides and the Python layout. VGC would need a second build, and the VGC reference digests would
  not be comparable any more. The capacity reading keeps one binary for both formats.
- **Cost of the capacity reading:** the views and the state carry one empty position per side. That costs a few hundred
  bytes per battle, measured in O2, not estimated here. A future layout change is a separate decision; this design
  does not need one.

### 2.3 Setup: EVs, IVs, level and the Tera type

`duoforge_member_setup` has `stat_points[6]`, `nature`, `ability` and `item`, but no IVs, no level and no Tera type
(`duoforge.h:189-202`). Adding fields would change the struct and with it `duoforge_battle_setup`.

- **Proposal: a sibling setup**, `duoforge_member_setup_<HS: ex>` with `evs[6]`, `ivs[6]`, `level` and `tera_type`, and
  a sibling create call `duoforge_battle_create_<HS: ex>`. The old call keeps its ABI. Under the OU kinds it refuses
  with `E_INVALID_ARGUMENT` (it cannot carry IVs); under the VGC kinds the sibling refuses everything that the old
  struct cannot express, so each kind has exactly one valid setup shape.
- Rules under the OU kind, from the format definition: EVs 0..252 per stat, at most 510 in all; IVs 0..31; level
  1..100, and `level` must equal the format's level unless the format allows less (Standard AG: at most 100; the
  definition records which). The stat formula is Gen 9's, with level, EV and IV terms (Champions' formula is
  `base + SP + 75` / `+ 20`, `src/data/formulas.c:6-16`).
- The replay importer and the live client pass EVs and IVs from the set or the prior; they never compute stats.

## 3. Tera (point 2)

### 3.1 State

- Per member: `tera_type` (one of 18 types plus Stellar, from the setup) and `terastallized` (0/1).
- Per side: `tera_used` (once per battle).
- These go into the state's tail under the OU kinds only. **The canonical encoding of every existing kind stays
  byte-identical**: the codec writes the Tera block only when the kind has Tera. `DUOFORGE_STATE_SCHEMA_VERSION`
  goes up when the tail format changes `<HS: version>`; the VGC digests are unaffected because their bytes are.

### 3.2 Rules (Gen 9, from the pin)

- The type becomes the Tera type (Stellar keeps the original types for defence).
- STAB: original types keep STAB; the Tera type gets STAB; a Tera type equal to an original type gives x2 instead of
  x1.5 (Adaptability x2.25); moves under 60 base power of the Tera type are raised to 60 (not multi-hit, not priority).
- Stellar: a one-time x2 per type (x1.2 on non-STAB types), and Tera Blast/Tera Starstorm forms. Tera Blast itself is
  banned in OU at the pin, so Tera Blast's category switch is out of the first scope and refused by name.
- Species specifics: Ogerpon (Embody Aspect on Tera, mask forms), Terapagos (Tera Shell, Teraform Zero) and the
  Tera-only forms are refused by name until their own step marks them.
- Every formula above gets its pin `file:line` in the step that builds it (O10); this list is a scope, not a proof.

### 3.3 Action

- Showdown submits Tera with the move (`move 1 terastallize`). The engine's Mega option is the precedent: the slot
  options gain a Tera variant of each move while `tera_used` is 0 and the member can terastallize. With singles that
  is at most 13 options, inside `DUOFORGE_MAX_SLOT_OPTIONS` (32).
- The command flag is a new value beside the Mega flag `<HS: DUOFORGE_SLOT_FLAG_TERA>`; it is refused under every kind
  without Tera.
- Order: Tera happens before moves, after switches, in speed order, as Showdown's `runAction` `terastallize` action.

### 3.4 View and information

- The foe's Tera type is **hidden** until the `-terastallize` line. The view gets `tera_type` per member as
  known/unknown (a tagged value, never "no type"), `terastallized` per member, and `tera_used` per side.
- These do not fit the existing reserve bytes cleanly; the observation extension's own rule applies: a larger struct
  is a new revision (`DUOFORGE_OBSERVATION_EXT_REVISION 1` → `<HS: 2>`). VGC callers keep revision 1.
- The hypothesis (`duoforge_view.h:89-99`) gets the foe's Tera types as a hidden value of the world, like stat points.
- New event kind `<HS: TERASTALLIZE>` with the type in `amount`; the observation digest classifier (decision 0082) gets
  the entry in the same PR (the content lane's digest rule).

### 3.5 Encoder

- Tera columns: per member the Tera type (known one-hot or unknown), terastallized; per side Tera available. They go into
  the OU encoder (section 6.4), never into encoder 6, which keeps its width (1094) and column order.

## 5. Coverage today (point 5)

### 5.1 Method

- **Source:** public Smogon monthly statistics, month **2026-09**, `chaos` JSON of format `gen9ou`
  (https://www.smogon.com/stats/2026-09/chaos/), retrieved 2026-10-14 20:36 UTC. 574,541 battles in the month.
- **Baselines:** for `gen9ou` Smogon publishes 0, 1500, 1695 and **1825**; there is no 1760 file for OU (1760 is the
  top baseline of the Champions formats). The top-player figure below is 1825; 1695 is listed for comparison.
- **Measure** (the content lane's measure, #413 handover): the share of all team slots that carry the entry. Per
  Pokémon, usage × the entry's weight on that Pokémon ÷ the Pokémon's total weight; coverage = the summed share of
  supported entries ÷ the summed share of all entries; empty moves and "nothing" items are excluded. Species: usage
  share of formes that are rows of the pool (aliases included).
- **Supported** = marked in `src/data/support_manifest.c` (moves, abilities, items) at f6b924a; species = a row of
  `src/data/pool_tables.c`. `classify_unsupported.py` is not on main yet (branch `content/classify-unmodelled`), so the
  committed tables are read directly.
- The raw files and the script stay outside the repository. Only shares are reported here.

- **The figures are an upper bound for Gen 9 semantics.** A mark proves the Champions variant. Of the 1825 coverage,

  sleeps or freezes runs through the overridden `par`, `slp` and `frz` conditions. These need a re-proof under Gen 9
  (step O9) before they count for OU.
- Zero coverage today: singles and Tera. So the number of playable OU battles today is 0, whatever the table says.

## 6. Networks: behaviour cloning on Gen 9 OU replays (point 6)

### 6.1 Sources, license and terms

- **The M11 source**, a public replay dataset on Hugging Face (`python/duoforge_replay/README.md`), is read from a local
  copy; the M11 spec records that the dataset states no license (`2026-10-02-m11-replay-data-design.md:51`). Whether
  it holds gen9ou games, and how many, is counted in O5 from the local copy. Nothing was downloaded for this document.
- **Showdown's own replay archive** (public replays uploaded by players). Its access terms and rate limits were not
  found in an authoritative source during this research; they are checked before any fetch, and any fetch goes through
  a documented, rate-limited path or not at all. Owner (Q6): the local dataset first; the archive only after its
  terms are checked.
- **What follows for us:** replays are user content without a stated license. Training is private, data and nets are
  never published, the repository holds aggregates only, and player names are stored only as hashes (as in M11).
  Redistribution of replays or derived rows is out of scope. If the owner wants a written basis, the question goes to
  the source's maintainers before the replay step (O5).

### 6.2 Filters

- **Format:** `formatid` exactly `gen9ou` (not `gen9oususpecttest`, not `gen9nationaldex*`); refused otherwise, and
  counted by reason.
- **Rating (default, Q3):** rows below 1500 dropped; weight 0.5 at 1500 rising linearly to 1 at 1700; unrated dropped.
  M11's VGC scheme (full weight at 1300) does not transfer: the OU ladder is larger and its rating spread is wider.
  An arm at ≥ 1700 only is measured beside it.
- **Bots and heavy accounts** (#413, 2026-10-12): a cap per account (weight or count), a list of known bot accounts
  (kept private, outside the repo), and the share they had in the manifest.
- **Refusals:** a game with an unsupported species, move, ability or item is stopped at the first line the view cannot
  represent, as in M11. The manifest counts decisions kept and dropped by reason; that count is the replay-side
  coverage figure.

### 6.3 Data volume

Not measured. OU is the most played Smogon format (574,541 rated battles in 2026-09 alone, from the statistics file);
the share with a saved public replay is unknown. The replay steps count it (O5 for Champions OU, O12 for Gen 9
OU). With today's Gen 9 coverage, most games stop early, so the useful volume grows with every O11 package.

### 6.4 Encoder for singles

- A new encoder version `<HS: E-OU1>`, valid only under the OU kinds; encoders 1–6 refuse an OU context and E-OU1
  refuses the VGC kinds. Encoder 6 keeps its width (1094).
- Layout: global; per side the head, **one** position block and six member blocks; Tera columns (section 3.5); hazard
  layers (existing ext fields); the candidate head over at most 32 slot options instead of 32 × 32 pairs; no
  team-selection head over 360 picks, a lead head over 6 instead.
- C and Python reference encoders stay byte-equal (decision 0021). The networks are keyed by encoder and format:
  `checkpoint.py` already stores `encoder`, `features` and an `ids` table; a checkpoint whose format differs is refused.
- The Champions OU milestone uses a singles encoder without Tera columns first (`<HS: E-S1>`, O4); E-OU1 adds the Tera
  columns for Gen 9 OU (O12). Both are format-keyed.
- **Training needs its own go from the owner.** O6 and O12 build the trainer path and run nothing without it.

## 8. Where to play (point 8)

Not the Showdown ladder first: Smogon's bot policy, and OU is the most visible stage (#413, 2026-10-14). **Owner

## 10. Risks and open questions

### Risks

- **Hidden ally assumptions.** About 350 index expressions assume two slots; some read slot 1 without checking for an
  occupant. The singles conformance set (O2) is the net; a missed case is a wrong result, not a crash, so the
  differential campaign is required, not optional.
- **Pool size.** The OU pool is several times the Reg M-C pool (458 species appear at baseline 0). Table id widths,
  the learnset bitmaps (`DFI_POOL_LEARN_BYTES`) and the generator's run time may not fit; O8 measures them.
- **Two semantics of one id.** Moonblast is 30 % SpA drop in Gen 9 and 10 % in Champions. Without a per-format manifest
  a VGC mark would silently count for OU. The per-format manifest (O9) is the guard.
- **Restructure overlap.** `docs/architecture/formats.md` and `data/formats/` belong to the restructure lane (step 10,
  not yet merged). This design reads them and changes neither; O1 starts after step 10 is merged, and the per-format folder is agreed
  with that lane (Q9).
- **Content-lane dependency.** The Champions OU milestone (O3) waits for the shared content the content lane builds
  under Reg M-C (Q5).
- **Replay terms.** No stated license; see 6.1.
- **Visibility.** OU is the most watched format; any public play needs the owner's go.
