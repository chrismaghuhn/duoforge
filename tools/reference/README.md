# Reference harness (pinned Pokemon Showdown)

Scripts here run against the pinned Showdown checkout (`b2cb775b0616115b775534eaeff50300e1fc81fc`, decision 0004) and turn its behaviour into committed C test data (decision 0006 section 7). CTest never needs Node: the generated files are committed, and the checks below run only when `-DDUOFORGE_PS_REFERENCE_DIR=<checkout>` is set and Node is found.

## `arith_ref.js`

Reference values of the damage and stat arithmetic: `Battle.modify`, `chainModify`, `Battle.randomizer` with a fixed roll, `Dex.trunc` and `Pokemon.calculateStat` on a real Pokemon of the format are called directly. The expressions the reference computes inline (base damage, the critical hit, type and final steps of `modifyDamage`, the accuracy stages) are evaluated with the reference's own `trunc` and cited in the script.

```sh
node tools/reference/arith_ref.js <checkout> > tests/reference/arith_ref.h
node tools/reference/arith_ref.js <checkout> --check tests/reference/arith_ref.h
```

CTest runs the `--check` form as `duoforge.reference.arith` (label `reference`). `duoforge.unit.modifier` compares `src/core/modifier.c` with the committed header.

## `ps_trace.js`

Records a complete battle. A spec (`tests/reference/specs/*.json`) gives the format, a PRNG seed, both teams as Showdown paste text (gender always given) and either the choices in request order (`choices`) or a plan (`plan`: per side the choices for its move requests in order, the last one repeated, and `max_steps`). In plan mode the harness answers team preview with the first four, a replacement with the first standing reserves and a fainted slot with `pass`; a planned move without PP falls back to the first move with PP, a target is dropped for a move that takes none and is 1 for a move that needs one. A planned switch of a trapped Pokémon (for example one charging a two-turn move) becomes "move 1 1". It records the choices it made. Draws inside a status or confusion handler are named by the effect and event the reference is running (sleep and confusion turns, freeze thaw, full paralysis, confusion self-hit). In the speed sort of `runSwitch` each Pokémon is labelled with its SwitchIn handlers and whether it is entering, in the speed sort of an `each:` event with the effects of its handlers; the snapshot records the weather and terrain durations and the moves each request offers. The harness runs the battle with a recording PRNG and writes a trace (`tests/reference/traces/*.json`): for every choice entry the draws it caused (site, context, bounds, value), the protocol lines and the state at the next boundary (exact HP, status, stages, PP, volatiles, active slots, requests).

```sh
node tools/reference/ps_trace.js <checkout> tests/reference/specs/s2_turn_core_1.json > tests/reference/traces/s2_turn_core_1.json
node tools/reference/ps_trace.js <checkout> tests/reference/specs/s2_turn_core_1.json --check tests/reference/traces/s2_turn_core_1.json
```

The site of a draw is read from its call stack, the context from the reference's event entry points, which the harness wraps (`queue`, `insert`, `switch-order`, `each:<event>`, `field:<event>`, `event:<event>`, and for random targets `action-speed`, `resolve` or `execute`). A draw it cannot classify is written as `UNKNOWN`; such a trace must not become a fixture. CTest reruns every spec as `duoforge.reference.trace.<name>` (label `reference`). Decision 0006 section 5.1 explains what the families mean for aligning DuoForge with the reference.

As a module, `require('./ps_trace.js')` gives `run(root, spec, specFile)`, `PIN` and `HARNESS_VERSION`. `run` records one battle from a parsed spec and returns the trace text, exactly what the command line prints; `root` is the checkout and `specFile` the spec's path, of which the trace stores the file name. It never exits the process: errors throw. The Showdown modules stay cached by `require`, so one process can record many battles. `run` first resets the state the harness keeps outside the battle (the event stack and the flags of the draw classification), so a run that threw leaves nothing behind. The command line is `run` plus the `--check` comparison. CTest records every committed spec in one process as `duoforge.reference.trace_run` (label `reference`): each result must equal its committed trace, a rejected choice must throw and leave the next run unchanged, and five specs (closure and Team C, one that ends the battle) run again in reverse order.

## `trace_to_c.py`

Turns every spec and trace into `tests/reference/conformance.h`: the teams in DuoForge ids, the slot commands per step, the expected members (HP, PP, stages, stall counter, the item still held), status, status counter and confusion turns, the boundary and result after the step, the occupants of the positions, the order of the entries, weather, terrain, Trick Room and the side conditions with their remaining turns, the moves each request offers, and the tape. Each player's view of the other side (seen members and their last public HP display) is rebuilt from the public copy of the protocol lines; a public HP that is not a Champions percent display stops the conversion. Each player's events of every step (decision 0007 section 11) are rebuilt from the protocol lines that player sees: the own copy of a split line for its owner, the public copy for the opponent; attributes that amend a move line are folded into its event, `[silent]` lines and hints are not events, and an unknown line or attribute stops the conversion. Residual ties between callbacks (burn, Grassy Terrain) are kept, because the engine draws them; entry-order ties are kept when two entering Pokémon have entry abilities; `each:` ties are kept when two tied Pokémon hold Sitrus Berry or Grassy Seed (their order is the order of their lines); when both sides' same side condition ends in one residual, the tie becomes an entry stating which side's end line comes first; queue-insertion ties among entries that run together and ties between screen handlers are dropped. The converter rejects a gender the species cannot have: the reference fixes it silently, DuoForge refuses the team. A `pass` the reference wants for a slot that a replacement does not ask becomes no command. A move for a slot whose request offers only Struggle becomes Struggle without a Mega declaration (the reference drops a typed `mega` with it); a slot without PP whose request is not Struggle stops the conversion. Draws without effect are dropped by named rules whose preconditions it checks (decision 0006 section 5.1); each step records how many were dropped. Shuffle draws become relative to their group. CTest checks that the committed headers are what the script makes of the traces (`duoforge.reference.conformance_tables`).

```sh
python tools/reference/trace_to_c.py .           # write the three headers below
python tools/reference/trace_to_c.py . --check   # compare them
```

It writes three files. `tests/reference/conformance.h` holds the closure battles and `conformance_team_c.h` the battles whose spec says `"data": "team_c"` (read with the extended tables). The record types of both (`df_conf_member`, `df_conf_step` and the others) are written to `tests/reference/conformance_types.h` from one template in the script; the two data headers include it, and so do the comparators of `tests/support/conformance_compare.c` (the checks of the replay, which later runners share).

The script is also a library (`import trace_to_c` from `tools/reference`). `load_battle(root, name)` reads a spec and a trace and is the only file IO of a conversion. `convert_battle(name, spec, trace, tables)` is pure and returns plain data in the field order of the `df_conf_*` types: the name, the purpose, the member count, the members as int tuples, and per step the `df_conf_step` fields, with the step's own tape entries (site, lo, hi, value) and each player's event tuples in place of offsets into the shared arrays, and the number of dropped draws; with the total dropped. `format_battle(data, out, all_tape, all_events)` writes that data as the C tables, appending to the shared tape and event arrays, and `spec_is_team_c(name, spec)` reads the Team C decision from a spec. `step_record(st, tape_off, ev_off, ev_len)` is one step as the nested int tuple of its `df_conf_step` in declaration order, the one place in Python where that order is written down; `format_battle` prints it, and a runner that writes records can flatten the same tuple (the member rows and the event tuples are in declaration order already). The drop rules stay in one place and are checked as before.

Whatever the converter does not model raises `ConversionError`, a `SystemExit` with a short stable `rule` (for example `protocol-line`, `unclassified-draw`, `residual-tie-callbacks`, `struggle-request`; it is the first argument of each `raise` in the script) and an optional `detail` that groups the cases (the protocol line kind, the attribute, the effects of the tie). The message is unchanged, so a script that does not catch it still prints it to stderr and exits with status 1.

CTest also runs `test_trace_to_c.py` as `duoforge.reference.converter_api` (Python only, no Node and no checkout). Its negative controls change in-memory copies of committed battles and assert the rule, the detail and the exact message of each refusal. It checks that the library reproduces the three committed headers, the shape of the data against the declarations of the record types (and `step_record` against the declared field names), that `convert_battle` does no file IO and leaves its inputs alone, that a choice passing both slots of a switch request converts, and the command line: `--check`, the usage message, a refused trace (status 1 and its message) and write and check of all three files on a small copy.

To add a battle: write a spec (gender for every gendered species), record its trace with `ps_trace.js`, run `trace_to_c.py`, and raise the battle count in `tests/test_conformance.c`.

The checkout needs `npm ci --ignore-scripts --omit=dev` and `node build` once, so that `dist/sim` exists.

## `gen_real_specs.py`

Reference battles of the real teams for the certification (decision 0010, M5 step 3). For each pairing (A-B, B-A, A-A, B-B) it builds candidate specs from `tests/reference/teams/team_a.txt` and `team_b.txt`: the six sets in a seeded random order (team preview brings the first four), a seeded random plan and a seeded reference PRNG seed (splitmix64, stable across Python versions). It records every candidate with `ps_trace.js`, drops traces with an `UNKNOWN` draw site or without a result, and keeps per pairing the battles that add the most coverage (protocol line kinds with their effect, draw sites with their context), greedily. The kept specs are written as `<prefix>_<pairing>_<k>.json` and recorded again from that path.

```
python tools/reference/gen_real_specs.py --checkout <pinned checkout> --candidates 40 --keep 4
```

With `--team-c` it builds the pairings of the Team C gate instead (decision 0009, step 12): C-A, C-B, A-C, B-C and C-C, with the real Team C of `docs/research/third-team/team-c.txt`, under the TEAM_C data kind. The defaults then are `--seed 2026100212 --prefix c12_real`, which reproduce the committed `c12_real_*` battles.

```
python tools/reference/gen_real_specs.py --checkout <pinned checkout> --team-c
```

## The differential loop: worker, records, runner, driver

The pieces below carry `docs/research/expansion/differential-testing.md` (components 1 to 4): a persistent worker records battles with the pinned Showdown (and plays random ones), the converter turns each trace into data, a C runner replays that data in the engine and compares, and a driver puts every battle in a bucket. Replay mode runs the committed specs; every one must come out PASS. Random mode plays battles with random choices that Showdown itself accepts and puts them in buckets too; its findings are what the loop is for.

### `ps_worker.js`

```sh
node tools/reference/ps_worker.js <pinned checkout>
```

One Node process that records many battles. It speaks JSON lines: one request per stdin line, one response per stdout line, in request order, nothing else on stdout (what a library prints goes to stderr). It exits at EOF.

```
{"id": n, "cmd": "version"}  ->  {"id": n, "ok": true, "node": process.version, "pin": PIN, "harness": HARNESS_VERSION}
{"id": n, "cmd": "record", "spec": <spec object>, "spec_file": "<basename.json>"}
                             ->  {"id": n, "ok": true, "trace": "<the trace text of ps_trace.run>"}
{"id": n, "cmd": "play", "battle": {"format": "...", "seed": "sodium,<64 hex>", "teams": [<p1 paste>, <p2 paste>]},
        "policy": {"seed": <uint32>, "max_steps": N, "switch_weight": 0.1, "mega_weight": 0.5, "domain_rate": 0.1}}
                             ->  {"id": n, "ok": true, "choices": [{"p1": "...", "p2": "..."}, ...], "ended": bool, "steps": n,
                                  "domain": {"samples": [{"step": k, "side": 0|1, "accepted": ["<text>", ...]}, ...],
                                             "request_changed": n}}
anything that throws, an unknown command, a line that is not a request
                             ->  {"id": n, "ok": false, "error": "<message>", "stack": "<first lines>"}
```

`id` is an integer the client chooses and gets back; a line that is not a JSON object with an integer `id` is answered with `"id": null`. A bad request never ends the worker. `record` is `ps_trace.run(checkout, spec, spec_file)` and nothing else: `spec_file` is the file name the trace stores (no directory), and the trace text is exactly what the command line prints, so the committed traces stay the reference. `play` is `ps_play.js` (below) and its choices go back as the `choices` of a spec, to be recorded by `record`: the trace that counts is always that recording, never the battle that was played. `play` refuses (ok:false) a request that has other keys than these (`domain_rate` is optional, 0 when it is not there), a seed that is not an integer from 0 to 2^32 - 1, a `max_steps` that is not a positive integer or weights and a rate outside 0 to 1. `duoforge.reference.worker_protocol` (label `reference`, needs Node and the checkout) checks the protocol over raw pipes: the answers and their order, a request that throws followed by a normal one, every kind of line it cannot use, that stdout stays clean, EOF, and that what `play` returns replays.

### `ps_play.js`

Random play with Showdown as the judge (the worker's `play`). Both sides of a plain `Battle` answer every request, `p1` first, as plan mode of `ps_trace.js` answers them, with a random choice drawn from the side's `activeRequest`: the team (four of the six, in random order, at team preview), a replacement (each slot that must switch takes a random standing reserve, else `pass`), or for each slot `pass` (empty or fainted), a switch with probability `switch_weight` (never when the request says the Pokemon is trapped), or a random enabled move with a random target (`battle.actions.targetTypeChoices` says whether it takes one, `battle.validTargetLoc` which of 1, 2, -1, -2 are allowed) and `mega` with probability `mega_weight` when the request says `canMegaEvo` and the other slot did not. **The policy knows no rules**: whether a text is allowed is Showdown's answer to `side.choose(text)`. A rejected text is cleared (`side.clearChoice()`) and a new one drawn; after 200 rejections every joint option of the side is enumerated in a fixed order and a random one that Showdown accepts is taken; if it accepts none the error is `no accepted choice`. The accepted text is committed with `battle.choose(id, text)` as `ps_trace.js` commits a recorded choice. The battle stops when it ends or after `max_steps` steps (`ended: false`).

**The domain of a request.** For the requests that `domain_rate` samples, `play` also returns every choice that Showdown accepts for the side: all the joint options of the side (the ones the fallback enumerates: for team preview the 360 ordered picks of four of six, for a replacement or a move request every `pass`, `switch` and `move` with its targets and `mega`), each judged with `side.choose(text)` and cleared with `side.clearChoice()` as the trials above are, and the texts that were accepted are the sample `{step, side, accepted}` (`step` is the index of the step the request is answered in, team preview is step 0). Which requests are sampled is not drawn by the policy's generator but decided by a hash of (policy seed, step, side) against the rate, documented in the file header: sampling never changes a choice of the battle, and a rate of 0.25 samples some of the requests that a rate of 1 samples, with the same sets. Judging can change a request (Showdown marks a move disabled or a Pokemon trapped when told so by an `Unavailable choice`, in the request and in the maybe-flags of the Pokemon): the request and the flags are put back as they were, and a sample whose request changed while it was taken is dropped and counted in `request_changed`.

The generator is its own and documented in the file header: sfc32 seeded by four outputs of splitmix32 of the policy seed (12 outputs discarded), in 32-bit integer arithmetic, so the stream is the same on every platform; unbiased `below(n)` by rejection, `chance(p)` an output below floor(p * 2^32), Fisher-Yates for the shuffles. It never touches the battle's PRNG, so the same battle seed and policy seed always give the same choices. `duoforge.reference.play_policy` (label `reference`, needs Node and the checkout) pins the generator and the sampling hash with known answers (checked against an independent implementation), tests how a choice is drawn, judged and enumerated on stand-in sides (and that a request that changes while it is judged is dropped and put back, in place), and plays real battles of the committed teams through `ps_trace.run` (no rejection, the same choices again, the recorded battle ends where the played one did) and with the domain sampled at rates 0, 0.25 and 1 (the same choices at every rate, every request sampled at 1, what was chosen among what was accepted, 360 picks at team preview).

### `conformance_records.py`

```sh
python tools/reference/conformance_records.py --all <repo root> --out <dir>   # closure.records and team_c.records
```

The records are what the C runner reads: one battle of `convert_battle`'s data as line-oriented ASCII, `B` (name, closure or Team C, the data kind, member count, step count, dropped draws, domain samples), `M` (a member row), then per step its domain samples `D` with their `C` records (random play only), `S` (the step record), its `T` lines (the kept draws) and its `E` lines (the events of player 0, then player 1's), and `END`. Every number is written; the format has no defaults. The field order is the converter's: the member rows, `step_record()` and the event tuples are flattened in the order they have, and the writer has no list of fields of its own. The offsets in a step record are into the tape and the events of its own battle. The format is described in the docstring of the module; `write_battle(data, team_c, out, kind=0, domain=())` writes one battle, all or nothing, and refuses (ValueError) what the format cannot hold.

A domain sample is the set of choices that the reference accepted from one side before one step (`D <step> <side> <count>`, then `count` records `C <18 numbers>`): a choice is the engine's side choice without its epoch and side (`kind`, `pick_count`, six picks, two slot commands of `kind move_slot target mega reserve`), what `trace_to_c.convert_choice` makes of a Showdown text, and `flat_choice` writes it. The choices of a sample are strictly ascending (as the 18 numbers read), so a set has no duplicate; the sample comes right before the `S` record of its step, side 0 before side 1, and only for a side that answers the step; the `B` line counts the samples (0 for the conformance records, which is what `--all` writes). The `df_conf_*` types are not touched: the sync tests read the samples into their own types (`dfr_domain`, `dfr_choice`) and require none in the conformance records.

The data kind of the `B` line says which context the runner must create the battle under, with no other to fall back on: `DUOFORGE_DATA_KIND_CLOSURE` (2) or `DUOFORGE_DATA_KIND_CLOSURE_DEV` (3) for a closure battle, `..._TEAM_C` or `..._TEAM_C_DEV` for a Team C battle (`data_kinds(root)` reads the numbers from `include/duoforge/duoforge.h`). 0 means the conformance fallback of the replay (the DEV context after the plain one), which is what the committed battles need and what `--all` writes. The reader refuses a kind that does not go with the closure or Team C flag of the same line.

CTest writes the records of all committed battles into the build directory (`duoforge.reference.records_write`, the setup of a fixture) and `duoforge.reference.runner_records` and `duoforge.reference.runner_records_team_c` read them with `tools/difftest/records.c` and require every battle, member, step, mon, tape entry and event to equal the compiled tables (`conformance.h`, `conformance_team_c.h`): `memcmp` of zeroed structs, the name and the per-battle offsets compared separately. Their negative controls flip one field of a copy of a parsed battle at a time (the comparison must report each one) and feed the reader damaged copies of a battle (each must be refused), among them damaged D and C records (a count that disagrees, a sample of another step or side, a side that does not answer, choices that are not ascending or are twice there, a pick that is not a member, a command outside its domain). The reader follows the `df_conf_*` declarations field by field, and static asserts on their sizes stop the build when a record type changes.

### `duoforge_diff_runner`

```sh
duoforge_diff_runner [records file]      # without a file: records on stdin
```

Built with the tests (`tools/difftest`; it links `duoforge_test_support`, which has the comparators, and is white-box like the conformance test). For each battle in the input it sets the teams up and picks the context exactly as `tests/test_conformance.c` does (closure battles under CLOSURE, then CLOSURE_DEV; Team C battles under TEAM_C, then TEAM_C_DEV) unless the battle names a data kind (the `B` line): then it creates the battle under that kind only, and a refusal is a finding (UNSUPPORTED for `DUOFORGE_E_UNSUPPORTED`, else DIVERGENCE) with the detail `create: <status> (<kind>)` and no second try. Without a kind the detail of a failed create names both statuses (`create: <status> (CLOSURE), <status> (CLOSURE_DEV)`). It steps with `dfi_battle_step_events_tape` (the reference's kept draws as the tape, which must be consumed exactly), then compares the state, the observations and the events with `df_conf_compare_*` and checks `duoforge_battle_check`. The first step with a difference ends the battle. Before a step is applied the runner checks the domain samples of that step (`tools/difftest/domain.c`): the engine's `duoforge_battle_candidates` for the side, each as a choice (the epoch and the side left out), against the set that the reference accepted, as sets (the engine's list is sorted, the reference's is ascending, a candidate listed twice is engine-only the second time). Any difference is a DIVERGENCE `domain: engine-only N, reference-only M (step K side S)`, with up to three examples of each kind in the messages (`  <name> step K: domain side S engine-only: slots move 1 -> 2 mega, switch 3`: a move is `move <move_slot> -> <flat target position or none>` and `switch <reserve>` names a roster index; a team choice is `team` and the picks); a candidates call that fails is `domain: candidates: <status> (step K side S)` (UNSUPPORTED for `DUOFORGE_E_UNSUPPORTED`). On stdout come the messages of the comparators (indented two spaces) and one flushed line per battle:

```
R <name> <PASS|DIVERGENCE|UNSUPPORTED> <CLOSURE|CLOSURE_DEV|TEAM_C|TEAM_C_DEV> <step|-> <steps> <detail>
```

The step is the first failing one (`-` for a PASS and for a battle that could not be created), `steps` is how many the records hold, and the detail is the rest of the line (`-` for a PASS). UNSUPPORTED: the create (after the DEV fallback) or a step returned `DUOFORGE_E_UNSUPPORTED`. DIVERGENCE: any other create or step failure (the status name is in the detail), a tape not consumed exactly (used of length), or a difference of a comparator or of the check. Exit status 0 at the end of the input, 2 for input that is not the format (a bug of whoever wrote it: stderr names the line), 1 for any other failure. Line ends are LF on every platform (stdin and stdout are binary on Windows).

`duoforge_diff_runner --dump-views FILE [records file]` also writes what DuoForge shows each player at every state the engine reached, for the Showdown live adapter's tests: after the create (`k` 0) and after every step whose comparisons passed (`k` = step + 1), one line per viewer, viewer 0 first: `V <name> <k> <viewer> <observation hex> <factored domain hex>` (`duoforge_battle_observe`, `duoforge_battle_factored`). A failing query is a DIVERGENCE `views: <status> (view K)` (step column: the step before view K, `-` for K = 0); a file that cannot be opened or written exits 1. Without the flag nothing changes. `duoforge.reference.dump_views` (`test_dump_views.py`) checks the lines of every closure battle and the first views of `m5_real_ab_1` against the public API.

### `ps_client.js`

```sh
node tools/reference/ps_client.js <pinned checkout> <repo root> (--all | NAME...) [--check]
node tools/reference/ps_client.js <pinned checkout> --pack <team file>
```

The client streams of committed closure battles: what a websocket client of each player receives. It replays each battle from its spec and its trace's recorded choices through a `Battle` whose output goes through `send` (with `sendUpdates()` after every command, as `BattleStream` does), shows the open team sheets at team preview, and writes one JSON object per message: `{"battle", "to": "p1"|"p2", "lines"}` (split lines resolved for the player, no timestamps). At this pin each update comes before its requests (`Battle.sendUpdates`). Every step's omniscient lines must equal the trace's, or it exits 1; `duoforge.reference.client_streams` runs it over every closure battle with `--check`. `--pack` prints `Teams.pack(Teams.import(text))`.

### `diff_driver.py`

```sh
python tools/reference/diff_driver.py replay --checkout <pinned checkout> --runner <duoforge_diff_runner> \
    [--workers N] [--only <glob>] [--out DIR] [--node <node>]
```

For each committed spec, in name order: the worker records it, and its trace must equal the committed trace (line ends as LF), else the battle is REF_ERROR ("trace differs from the committed trace"; a worker answer `ok: false` is REF_ERROR with its error). `trace_to_c` converts it: a `ConversionError` is ORACLE_GAP with its rule and detail, and a `KeyError`, `IndexError`, `ValueError` or `TypeError` out of `convert_battle` is ORACLE_GAP with the rule `untyped:<ExceptionType>` and the message and the function and line that raised it as detail; nothing else is caught. The records go to the runner, whose line gives PASS, DIVERGENCE or UNSUPPORTED, with its messages. Every battle is in exactly one of the five buckets.

`--workers` threads (default 4) each own one Node worker and one runner, started below normal priority (`BELOW_NORMAL_PRIORITY_CLASS` on Windows, nice 10 elsewhere) so the machine stays usable. A child that dies or does not answer in 300 seconds on a battle is a bucket of that battle: a runner is a DIVERGENCE (`runner died (exit X)`, `runner timed out`: the engine crashed or looped on it), a worker a REF_ERROR (`worker died (exit X)`, `worker timed out`); the last lines it wrote to stderr are the messages, and the child is replaced before the next battle. A child that answers out of protocol, cannot be started, reports another version, leaves with a status at the end, or a runner that refuses its input (exit 2: a bug of the writer of the records) is a failure of the tool, not a bucket: the run stops with status 3 and writes nothing. `--out` (default `build/diff/<UTC yyyymmdd-hhmmss>-replay`) gets `battles.jsonl`, one line per battle in name order (`name`, `bucket`, `rule`, `detail`, `step`, `steps`, `context`, `messages`; `null` where there is nothing; for ORACLE_GAP the message is the converter's), and `summary.json` with the counts per bucket and per rule, the Node version, the pin, the harness version, the git HEAD and the library version (from `duoforge.h`). Neither file depends on thread timing. Exit status 0 only if every battle is PASS, 1 if one is not, 2 for a bad command line, 3 for a failure of the tool. The driver only orchestrates: the rules are the converter's and the engine's.

`duoforge.reference.diff_replay` (label `reference`, needs Node and the checkout) runs it over all specs with 4 workers. `duoforge.reference.diff_driver` needs Python only: it feeds fake workers and runners to the bucket logic and the order of the output (the converter is real, the refusals come from edited copies of committed battles), runs the child clients against stand-in processes, tests the records writer, and, with the runner this build makes (`DUOFORGE_DIFF_RUNNER`, which CTest sets), takes every committed battle through the driver with a stand-in that answers the committed traces.

### `diff_driver.py random`

```sh
python tools/reference/diff_driver.py random --checkout <pinned checkout> --runner <duoforge_diff_runner> \
    --battles N --seed S [--pairings AB,BA,AA,BB] [--workers W] [--out DIR] [--start K] \
    [--chunk-minutes M] [--no-lock] [--node <node>] [--max-steps 300] [--switch-weight 0.1] [--mega-weight 0.5] \
    [--domain-rate 0.1]
```

Battles that the pinned Showdown plays itself, put in buckets: this is the mode that finds things (`diff_random.py`; the driver only orchestrates).

**Battle `i` of run `S`** follows from `(S, i)` alone, not from the other battles, `N`, the workers or the chunks. Its pairing is `pairings[i % len(pairings)]`: `A` and `B` are `tests/reference/teams/team_a.txt` and `team_b.txt`, `C` is `docs/research/third-team/team-c.txt` (a pairing with C, `CA AC CB BC CC`, is Team C data, spec `"data": "team_c"`, and opt-in: the default is `AB,BA,AA,BB`). The order of the six sets of each team, the reference seed and the policy seed come from `gen_real_specs.py`'s `SplitMix64` and `shuffled` (imported, not copied), seeded with `battle_seed(S, i)`: two splitmix64 steps, `SplitMix64(SplitMix64(S).next() ^ (i * 0x9E3779B97F4A7C15 mod 2^64)).next()`. The name is `fz_<S>_<i>`; the purpose of its spec says that it is a random differential battle `i` of run `S`.

**Pipeline and buckets.** Each battle goes through five steps and lands in the bucket of the first one that ends it:

| step | what | bucket when it ends there |
| --- | --- | --- |
| play | the worker plays it (`ps_play.js`: random choices that Showdown accepts) | REF_ERROR: the worker said no (`no accepted choice`, a Showdown error) or died or hung (`worker died (exit X)`, `worker timed out`) |
| record | the worker records the resulting choices spec (`ps_trace.run`) | REF_ERROR `the choices spec does not replay`: the recording throws, or the battle ends other than the play said (the trace is always this recording) |
| convert | `trace_to_c`, for the battle and for each domain sample | ORACLE_GAP: a `ConversionError` or, as in replay mode, an untyped error (`untyped:<ExceptionType>`); REF_ERROR `a domain sample disagrees with the recording` when what was played is not in the set that Showdown accepted for that request, or the sample is of a side that did not answer the step |
| run | the runner creates and steps the battle, and compares the domain before each sampled step | UNSUPPORTED or DIVERGENCE as the runner says (`domain: engine-only N, reference-only M (step K side S)` for a difference of the domain); a runner that dies or hangs is DIVERGENCE `runner died (exit X)` or `runner timed out` |
| end | the runner said PASS | CAP if the battle did not end within `--max-steps` (default 300), else PASS |

Every battle is in exactly one of the six buckets. A child that dies or hangs is a bucket, never the end of the run: the battle is saved as a case, the child is replaced, and the run goes on (a worker is given 300 seconds per answer, a runner 60 per battle). A failure of the tool itself (a child that speaks out of protocol, cannot be started or reports another version, a directory that belongs to another run) stops the run with status 3.

**The context is strict.** The records name the data kind the runner must use, and the runner has no fallback under it: random battles of teams A and B run under `CLOSURE`, Team C battles under `TEAM_C`; there is no DEV context. A real team that the kind rejects is a finding, and its `create:` detail names the status and the kind.

**The domain check** (`--domain-rate`, the share of requests, 0.1 by default, 0 for none). The worker returns, for the requests that its hash picks, every choice that Showdown accepts for the side (see `ps_play.js`). The driver makes each text the choice that `trace_to_c.convert_choice` makes of it, called as it is with the state before the step, the roster of the battle and the mid-turn flag, exactly as the converter calls it for what was played (the driver builds those the way `convert_battle` does and a test requires that for every committed battle, played choices give what the converter has in its data), and the set, canonical and in ascending order, goes with the battle in D and C records. Several texts can be one choice (a locked move takes any text); a text that `convert_choice` refuses is a gap of the oracle. The runner compares the set with the engine's candidates before the step (see the runner above). Prefixes carry the samples of their steps. `battles.jsonl` has per battle `domain: {samples, request_changed}` (null when the play failed) and `summary.json` the rate and the totals. The rate is part of the identity of a run (`run.json`).

**Cases.** Every battle that is not PASS gets `cases/<name>/`:

```
spec.json            the spec, with its choices once there are any: the shape of a committed spec (copy it to promote it)
trace.json.gz        the recording of that spec, if the pipeline got that far (gzip without a name or a time: the same bytes every time)
play_request.json    {battle, policy}: what the worker was asked, when the play failed
messages.txt         "<bucket> | <rule> | <detail>", then the messages of the converter, the comparators or the child's stderr
step.json            DIVERGENCE with a failing step: that step's input, protocol lines and draws, each draw with what
                     trace_to_c.drop_reason makes of it (kept, dropped: <reason>, or the error it raises)
domain.json          DIVERGENCE of the domain: the sample of that step and side, every text Showdown accepted with its
                     choice as the runner prints it ("slots move 1 -> 2 mega, switch 3"), to find the texts of a choice in
                     the examples of the messages
prefix_spec.json     the choices up to and including the failing step (CAP: all of them), as a spec
prefix_result.json   what the driver found when it ran that prefix through the same pipeline
```

For a DIVERGENCE with a failing step and for a CAP the driver runs the prefix and records in `reproduces` whether it comes to the same bucket at the same step again.

**Output.** `--out` (default `build/diff/<UTC yyyymmdd-hhmmss>-random-s<S>/`) gets `battles.jsonl` (one line per battle in index order: `index name pairing bucket rule detail step steps context ended reproduces domain messages`), `summary.json` (the parameters and versions, the count per bucket and the signatures below with their count, the first battle and the case to look at, how many prefixes reproduced, and the domain: the rate, the requests sampled, how many of them are in battles that ran to the end with the engine's candidates equal to what Showdown accepts at every sampled step (`agreed`: PASS and CAP battles) and the samples dropped because their request changed) and `timing.json` (seconds per phase, per chunk, and the slowest battles). `battles.jsonl` and `summary.json` hold no timing and are the same for the same run however it ran: with one worker or six, in one chunk or in forty. `run.json` is the identity of the run (parameters, Node version, pin, harness, git HEAD, library version and the SHA-256 of the runner): a chunk refuses a directory that belongs to another run. `partial/` holds the result of each finished battle (written whole or not at all, after its case), `cases/` the cases.

**Signatures.** `summary.json` counts non-PASS battles per `(bucket, rule, detail)`, so that a hundred times the same thing is one line: the rule and detail of the converter for ORACLE_GAP, the error for REF_ERROR; for the runner's UNSUPPORTED and DIVERGENCE the kind of difference with its numbers left out (`create: <status> (<kind>)`, `step: <status>`, `tape: not consumed exactly`, `state: <the first message of the comparator with # for each number>`, `observation: ...`, `events: reference kind K differs in <the fields>`, `battle_check: <status>`, `domain: engine-only <kinds>, reference-only <kinds>` where the kinds are those of the printed examples (`team`, or the command of each slot joined by `/`: `move`, `move+target`, `move+mega+target`, `switch`, `pass`, `none`) and `domain: candidates: <status>`, `runner-failed: died (exit X) | timed out`).

**Chunks and the machine lock.** The machine is shared, so a long run does not hold it for hours: without `--no-lock` the driver loops over chunk subprocesses, each `bash tools/ci/machine_lock.sh fuzz <python> diff_driver.py random ... --start K --chunk-minutes M --no-lock` (`M` defaults to 10): the chunk waits for the lock, starts no battle after `M` minutes, finishes the ones that are running and exits with its results written; the lock is free for 30 seconds between two chunks, so a CI or a benchmark that waits gets it, and the next chunk goes on at the first battle without a result. Because the files are made of the results by battle index, the chunking cannot change them (the unit test runs the same battles in one chunk and in several and compares the bytes). `--no-lock` runs all battles from `--start` in this process, without the lock and without chunks; CTest uses it because `local_ci.sh` holds the lock already. An explicit `--chunk-minutes` with it makes the process one chunk, which writes the results of its battles and no summary: the files of the whole run are written by the process that owns it, the loop above or a run without `--chunk-minutes` once every battle has a result. Running the driver again with the same arguments and `--out` goes on where it stopped. The children run below normal priority, and `DUOFORGE_MACHINE_LOCK` names another lock directory (the tests use a temporary one, never the real lock).

Exit status: 0 when the run is complete (the findings are in the files, not in the status), 2 for a bad command line, 3 for a failure of the tool.

`duoforge.reference.diff_random` needs Python only: the derivation of battle `i` with pinned values, the bucket of every step of the pipeline and which one wins (a committed battle stands in for the reference, with faults made by index), the signatures, the cases, the cut into chunks and the files that must not depend on it, children that die or hang (stand-in processes), the lock in a temporary directory, the command line, the domain samples (the canonical choice of what was played equals what the converter made of it, in every committed battle of a sample; samples are written before their steps, counted and cut with the prefix; a sample that contradicts the recording; the signatures and the case file of a difference of the domain), and, with the runner this build makes (`DUOFORGE_DIFF_RUNNER`, which CTest sets), committed battles through the real runner under the strict kinds and with a domain at team preview (the same set passes, a pick taken out is engine-only, a switch to a Pokemon in the field put in is reference-only). `duoforge.reference.diff_random_smoke` (label `reference`, needs Node and the checkout) runs 16 battles of `AB,BA,AA,BB` with seed 2 and 2 workers, twice as one run and once in pieces (the second half as a chunk, then the rest, then a run that writes the files), and requires byte-identical files and the buckets, signatures and lengths of `tests/reference/random_smoke_golden.json` (`tools/reference/test_diff_random_smoke.py ... --update-golden` writes it after a change that is meant to change them). `duoforge.reference.runner_domain` (C, no Python or checkout) tests the comparison of the engine's candidates with a set of choices on real candidates of the fixtures, with the controls that make it worth anything: a choice taken out comes out engine-only, one put in reference-only, a candidate listed twice engine-only, the examples are the first three in order, and the text of a choice is pinned. `duoforge.reference.diff_domain_smoke` (label `reference`, needs Node and the checkout) runs 8 battles of `AB,BA,AA,BB` (seed 6) with every request sampled (`--domain-rate 1.0`: a few hundred requests) and requires them all PASS, every sample in agreement, and the same battles without the check to come to the same bucket, length and end: sampling changes nothing else.
